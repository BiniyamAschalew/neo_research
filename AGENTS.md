# AutoResearch Codex Adapter

This project uses AutoResearch to coordinate Codex, Claude, and the human through a shared board.

## Shared Board

All project state generated by agents must live under `__board__/` at the project root:

- `__board__/STATUS.md`: shared project status.
- `__board__/plans/`: iteration plans.
- `__board__/reports/`: implementation reports.
- `__board__/notes/`: technical notes.
- `__board__/refs/`: project reference material.

Do not write generated research state into `.claude/`, `.codex/`, or `.agents/`.
Those directories define agent behavior and configuration only.

Do not create `__board__/` during ordinary session startup. AutoResearch skills create it lazily when invoked and create only the subdirectories required by that workflow.

## Session Startup Checklist

At the beginning of a Codex task:

1. Read `__board__/STATUS.md` if it exists.
   Also read `__board__/PROJECT.md` (project specifics) and `~/.config/ar/host.md` (machine rules, such as GPU claims) when they exist; they override shared defaults. If `host.md` is missing on a GPU server, check `hosts/` in the neo_research checkout for that machine's rules before running GPU jobs.
2. If executing a plan, read the relevant file in `__board__/plans/`.
3. Scan recent files in `__board__/reports/` and `__board__/notes/` when they are relevant.
4. Do not create `__board__/` during startup. Let the invoked AutoResearch skill create only the paths it needs, and never overwrite existing board files during bootstrap.

## Codex Skills

Use the AutoResearch skill names:

| Skill | Usage | Description |
|-------|-------|-------------|
| `$ar_plan <task>` | `$ar_plan Implement preprocessing` | Generate a plan under `__board__/plans/` |
| `$ar_dev [plan]` | `$ar_dev v3.preprocessing` | Execute a plan and write a report under `__board__/reports/` |
| `$ar_note <topic>` | `$ar_note optimizer comparison` | Write a technical note under `__board__/notes/` |
| `$ar_tree new\|close <slug>` | `$ar_tree new head-swap` | One worktree per idea; only a summary returns to main |
| `$ar_compact [scope]` | `$ar_compact idea x into dir/y` | Same results, less code, before promote/graduate |
| `$ar_mate [request]` | `$ar_mate status` | First mate coordinating idea worktrees in Herdr |
| `$ar_goal [goal.yaml]` | `$ar_goal` | Overnight one-change-at-a-time improvement loop |
| `$ar_notify [report]` | `$ar_notify __board__/reports/v3/v3.md` | Slack text summary of a finished run |

Claude uses matching slash commands instead: `/ar_plan`, `/ar_dev`, `/ar_note`, `/ar_tree`, `/ar_compact`, `/ar_mate`, `/ar_goal` and `/ar_notify`.

Launch experiment runs through `python .agents/skills/ar_notify/scripts/notify_run.py -- <command>` so every completion posts to this project's Slack channel and its runs log to this project's W&B workspace (settings in `__board__/project.env` of the main checkout; never print or commit that file).

## Python Environment

Use the existing project environment when one exists. Prefer `uv` when available, but `pip install` is allowed when necessary.
Document any dependency installation in the relevant report or note.

Common commands:

```bash
# Activate an existing venv if present
source .venv/bin/activate

# Preferred when uv is available
uv pip install -r requirements.txt
uv pip install <package>

# Allowed when necessary
pip install -r requirements.txt
pip install <package>
```

## Development Rules

- Read the relevant plan before editing code.
- Keep changes scoped to the selected plan unless the user explicitly expands scope.
- Run relevant tests required by the selected plan or explicitly requested by the human. Do not add broad unrelated verification by default; if no tests are planned or requested, document `Verification: not required by plan or request` when a report is produced.
- Save plans, reports, and notes under `__board__/`.
- Do not overwrite another agent's board file unless the human explicitly asks.
- Do not run `git push` without explicit human instruction.
- Preserve existing project code style and conventions.
- When a requirement is ambiguous during `$ar_dev`, make a reasonable decision, proceed, and document the decision in the report.
